# BF-003 地点检索并发超限触发百度短信告警（4/3）

- 日期：2026-10-01 　提交：e0f4101 　影响模块：`core/config`（默认值）`.env` `.env.example`

## 现象

切真实模式后，一次地址搜索 + 一次"检索周边设施"，用户收到百度短信：

> 您使用的地点检索服务并发量已经接近约定上限（4/3），为不影响正常使用，请登录官网提交工单。

## 根因分析

短信里 4/3 = **瞬时并发 4 个请求 / 契约上限 3**（并发超限，不是总量配额耗尽）。

触发链：一次设施检索 = 4 个类目（医疗/教育/购物/养老）`asyncio.gather` **同时**发起 place 请求；
而默认限流 `api_qps=5, api_burst=10` 的令牌桶对此毫无约束——4 个请求全部瞬间放行。
旧默认值是按"按账号配额调整"的通用口径拍的，没有对齐免费档地点检索的并发契约。

## 修复方案

- `config.py` 默认值：`api_qps 5 → 2`、`api_burst 10 → 3`（铁律 #4：外部约束全配置化的正确姿势是默认值就对齐契约）
- `.env.example` 同步并注明原因；存量 `.env` 中的 `OPENMAP_API_QPS` 盲改（不读文件内容，避免密钥入上下文）
- 修复后四类目并发由令牌桶自然排队：前 2 个立即发出，第 3 个等 0.5s、第 4 个等 1s → 瞬时并发 ≤ 3

## 验证结果

- 后端四链全绿（ruff format/check、mypy 34 files、pytest 58 passed）
- 用户实测：修复后连续检索不再收到告警短信，检索结果正常返回（延迟 +1~2s，排队代价）

## 影响范围与注意事项

- 所有并发调用百度 API 的链路（含 M3 覆盖率分析）都被此默认值保护
- 若申请到更高并发（工单/企业版），只需调 `.env` 的 `OPENMAP_API_QPS/OPENMAP_API_BURST`，无需改码
- **复发信号**：再收并发告警短信，或响应中出现 RATE_LIMIT 类错误（适配器会退避重试，但说明配置超了契约）
