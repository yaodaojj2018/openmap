# 《基于地图开放能力的"15 分钟生活圈"智能体检与规划助手》需求分析报告

> 命题来源：`ai_15_nIsJ99EN3y.pdf`【开源 AI 工具赛道】
> 分析定位：架构级需求分析（不含代码实现）
> 报告日期：2026-09-18

---

## 1. 命题背景与痛点深度解析

### 1.1 政策背景

国家层面推行"15 分钟便民生活圈"建设，要求居民在**步行 15 分钟范围内**可获得：

- 基础医疗
- 教育
- 购物
- 养老

四类核心民生服务。

### 1.2 现状痛点（命题原文拆解）

| # | 痛点 | 本质问题 | 对产品的启示 |
|---|------|---------|------------|
| P1 | 社区规划依赖**人工普查 + 静态数据**，缺乏"真实可达性"的动态考量 | 评估模型维度单一，只看"有没有"，不看"到不到得了" | 核心卖点必须是**基于真实路网的可达性**，而非直线半径画圆 |
| P2 | 道路并非直线：红绿灯、过街天桥、施工围挡极大影响实际步行可达范围 | 直线距离 ≠ 步行耗时；几何近似严重失真 | 必须以"**步行时间**"为一等公民度量单位；等时圈形状应不规则、贴合路网 |
| P3 | 传统评估手段成本高、更新慢，无法精准发现"服务盲区" | 人工评估不可重复、不可规模化 | 系统须**自动化、可重复、低成本**：输入一个坐标即可出报告 |

### 1.3 命题隐含的关键约束（决定技术选型）

> ⚠️ 评审细则 30% 维度中明确：**"鼓励在不获取底层路网数据的前提下，通过对周边分散点位的 API 测时结果进行空间插值或扇形采样，合理推导出近似连通区域"**。

这是全命题最关键的技术约束：

1. **不允许（或不依赖）下载/爬取底层路网图数据**（如 OSM 路网 + 图算法的传统等时圈方案不是命题鼓励路线）；
2. 等时圈必须通过**地图开放 API 的路径规划/测距结果**间接推导；
3. 这既是约束，也是 30% 权重中的**加分创新点**。

## 2. 命题目标解读与核心业务逻辑

### 2.1 产品定位

- **形态**：Web 应用或小程序（二选一即可，Web 更利于评审演示与 CI/CD）
- **地图底座**：百度地图开放能力（含但不限于）：
  - 地理编码 / 逆地理编码
  - POI 兴趣点检索
  - 路径规划与距离计算（步行路线规划、批量距离矩阵）
- **目标用户**：社区规划人员、街道办、民政/商务部门（B 端工具属性）

### 2.2 核心业务流水线（Pipeline）

```
[输入] 中心点坐标（或地址 → 地理编码）
   ↓
① 等时圈计算：基于真实路网推演"15 分钟步行等时圈"
   ↓
② POI 覆盖统计：分类检索圈内民生设施，判定"路网可达"归属
   ↓
③ 体检报告生成：分类覆盖率评分 + 可视化图表
   ↓
④ 盲区识别与标注：标出设施匮乏的"灰色区域"（重点：1km 内无菜市场/药店/小学的点位）
   ↓
[输出] 可视化"体检报告"
```

### 2.3 核心业务逻辑要点

1. **选点**：用户选定某城市任一社区/街道作为样例，输入中心点坐标（需支持地址 → 坐标的地理编码转换，因为用户更可能输入"XX 路 XX 号"）。**增强**：支持输入 1~3 个小区出入口（大社区单中心点无法代表居民实际出发点），代表中心自动取出入口质心。
2. **等时圈计算**：以中心点为源点，计算真实路网约束下 15 分钟步行可达范围。步行速度行业惯例 60~80 m/min（约 4~4.8 km/h），即路网距离约 900~1200 m——这决定了采样半径量级。**多出入口时**从每个出入口各算一遍并取并集（MultiPolygon，见 docs/02 §3.1.5）。
3. **覆盖统计**：检索圈内四类民生设施（医疗/教育/购物/养老），统计"**路网可达**"的设施数量与分布（注意：判定标准是路径规划耗时 ≤ 15 min，不是直线距离落圈）。
4. **体检报告**：输出分类设施的覆盖度评分（雷达图/柱状图数据源）+ 等时圈热力图。
5. **盲区标注**：识别并可视化"灰色区域"——命题给出硬指标：**周边 1 公里内没有菜市场、药店或小学的"服务盲区"点位**。口径说明：盲区是「1 公里直线距离」独立口径，**独立于 15 分钟等时圈**，灰色区域落在等时圈之外属正常（双口径并置，见 Q3）。

## 3. 关键功能模块划分

建议六模块架构（对应评分维度均有覆盖）：

### M1 地图能力接入层（API Adapter / Gateway）

| 子功能 | 说明 |
|-------|------|
| 地理编码/逆地理编码 | 地址 ↔ 坐标互转；坐标纠偏 |
| POI 检索封装 | 圆形区域检索、关键词/类目检索、**分页翻页**（单页上限通常 20 条，需翻页聚合） |
| 步行路径规划 | 单源单目标，返回距离 + 耗时 |
| 批量距离矩阵 | 单源多目标批量测距测时（降低调用次数的关键手段） |
| 限流/重试/缓存 | 令牌桶 QPS 控制、指数退避重试、熔断降级、结果缓存 |

### M2 等时圈计算引擎（核心算法模块，命题最大亮点）

- **扇形采样器**：以中心点为极点，按 N 方向（16/32/64）发射采样射线，每方向沿距离递增探测路径规划耗时；
- **最远可达点求解**：每方向用二分/折半搜索定位"耗时 = 15 min"的临界点；
- **边界拟合**：将各方向临界点插值（Catmull-Rom / 样条）或包络（alpha-shape/凹包）成闭合多边形；
- **多级等时圈**：支持 5/10/15 min 嵌套圈（报告层次感 + 展示效果加成）；
- **自适应分辨率**：边界变化剧烈方向加密采样，平坦方向稀疏采样（省 API 配额）。

### M3 POI 采集与清洗模块

- 分类目策略检索（菜市场、药店、小学、社区卫生中心、养老驿站等）；
- 去重（同名连锁、坐标 10m 内聚类）、停业/异常 POI 过滤；
- 类别归一化（百度 POI tag → 本系统四大类映射表）。

### M4 覆盖统计与盲区识别模块

- 覆盖判定：设施 → 中心点（或反向）路径规划耗时 ≤ 15 min 即"圈内可达"；
- 分类覆盖率计算（数量密度、可达率、均耗时等多指标）；
- **盲区识别算法**：区域网格化（50~100 m 栅格）+ 关键三类设施（菜市场/药店/小学）1 km 邻域判定 → 无覆盖栅格聚合为"灰色区域"多边形。

### M5 可视化与交互前端

- 地图端：等时圈热力图（多层嵌套）、POI 分类打点、盲区灰色多边形标注；
- 图表端：柱状图（分类设施数）、雷达图（四大类覆盖评分）；
- 交互：自定义中心点（地图点选 + 地址输入双入口）、进度反馈、报告导出。

### M6 工程化与部署模块

- Docker Compose 一键起服务（前端 + 后端 + 缓存）；
- 环境变量配置管理（API Key 脱敏，`.env.example` 模板）；
- 自动化测试脚本（等时圈算法单测 + API mock 集成测试）；
- CI/CD（GitHub Actions / Gitee Go：构建 + lint + 测试）。

## 4. 输入输出规范（I/O Spec）

### 4.1 系统输入

| 输入项 | 类型 | 必填 | 约束与说明 |
|-------|------|-----|-----------|
| 中心点坐标 | `lng, lat` | 二选一 | **必须明确坐标系**：百度 API 为 BD09，前端地图拾取器默认 BD09；若允许外部粘贴 GCJ02/WGS84 坐标需转换 |
| 中心点地址 | 字符串 | 二选一 | 经地理编码转坐标，需处理歧义（多候选、区县级模糊匹配） |
| 步行时长阈值 | 数值（分钟） | 否 | 默认 15，建议支持 5/10/15 |
| 步行速度 | 数值 | 否 | 默认 4 km/h 级别（部分 API 内置耗时，可不暴露） |
| 设施类别清单 | 多选 | 否 | 默认四大类全选（医疗/教育/购物/养老） |
| 盲区判定半径 | 数值 | 否 | 命题硬指标 1 km，作为默认值 |

### 4.2 系统输出

| 输出物 | 形式 | 规范要点 |
|-------|------|---------|
| 等时圈 | GeoJSON `Polygon` / `MultiPolygon` | 多级圈嵌套；**必须支持 MultiPolygon**（河流/铁路切割产生飞地）；属性含 timeLevel |
| 设施清单 | 结构化列表 | 名称、类别、坐标、路网距离(m)、步行耗时(min)、是否圈内 |
| 体检报告评分 | JSON + 页面渲染 | 四大类各自：数量、覆盖率、平均耗时、评分(0~100) |
| 盲区列表 | GeoJSON + 标注 | 灰色多边形/点位 + 缺失设施类型标签（无菜市场/无药店/无小学） |
| 报告导出 | 图片 / PDF / JSON | 评审与存档需要 |

### 4.3 中间数据规范（API 响应解析）

- 路径规划响应：提取 `distance`、`duration`，注意步行规划的 `duration` 已含过街/信号灯因素的近似值（这正是"真实可达性"的数据来源，需在文档中论证）；
- 批量矩阵响应：目的地点序映射关系不可错位；
- 错误响应：按错误码分类（配额超限 / 参数错 / 无路线 / 服务忙），进入不同降级分支。

## 5. 边界条件与异常场景清单

### 5.1 地图 API 侧

| 场景 | 后果 | 处置要求 |
|------|------|---------|
| QPS 超限 / 日配额耗尽 | 批量请求被拒 | 令牌桶限速 + 请求排队 + **缓存复用**（关键：评审演示不能因配额卡死） |
| API 超时 / 5xx | 单点采样失败 | 指数退避重试（≤3 次）→ 失败点降级用邻方向插值补齐，不让整体失败 |
| POI 检索结果为空 | 新城区/城郊可能无菜市场 | 空结果兜底：明确报告"该类设施 0 个"，而非报错 |
| 坐标系混用（BD09/GCJ02/WGS84） | 偏移 100~600 m，等时圈整体错位 | 全链路统一坐标系，入口处做一次性转换并在文档说明 |
| 地理编码歧义 | 同名道路多城市命中 | 返回候选列表让用户选择，或城市约束参数 |
| 路径规划"不可达" | 河流对岸、高速路隔离带、封闭园区 | 不可达 ≠ 距离无穷大的简单处理；需标记"该方向受阻"，用于解释圈形凹陷 |

### 5.2 算法侧

| 场景 | 后果 | 处置要求 |
|------|------|---------|
| 采样点落在不可达位置（水域/建筑内部/景区封闭区） | 该方向测时失败 | 剔除 + 邻近方向插值；不影响整体 |
| 等时圈非凸、含空洞、含飞地 | 单 Polygon 表达失真 | MultiPolygon + 空洞表达；拟合算法不能强制凸包 |
| 中心点位于偏远地区 | 等时圈极小甚至退化为点 | 提示"该区域路网稀疏，结果仅供参考" |
| 采样密度 vs API 成本矛盾 | 全方向高精度采样配额爆炸 | 两级采样（先粗后细）+ 变化率自适应加密 + 结果缓存 |
| 批量矩阵单次目的地数量上限 | 一次查不完所有 POI | 分批 + 并发（在 QPS 约束内） |

### 5.3 数据侧

| 场景 | 后果 | 处置要求 |
|------|------|---------|
| POI 重复（连锁多分店、数据源重复） | 设施数量虚高 | 名称相似 + 距离 <30 m 聚类去重 |
| POI 分类噪音（"医药公司"混入"药店"） | 覆盖率虚高 | 类目白名单 + tag 过滤规则，写入清洗文档 |
| POI 数量巨大（市中心上千点） | 前端渲染卡顿 | 聚合（cluster）渲染 + 仅圈内点全量展示 |

### 5.4 交互侧

| 场景 | 处置要求 |
|------|---------|
| 中心点选在海面/无路网区域 | 前置校验 + 友好提示 |
| 用户连续拖动/改点 | 请求防抖 + 取消过期请求（竞态控制） |
| 全流程计算耗时较长（分钟级） | 异步任务 + 进度条（"采样 12/32 方向"）+ 结果缓存 |
| 评审环境无有效 API Key 或配额不足 | **演示数据兜底**：内置离线示例数据模式，保证一键跑通 |

## 6. 潜在技术难点与应对策略

### 难点 1：无底层路网数据条件下的等时圈生成（★ 最高优先级）

- **难点本质**：传统等时圈 = 路网图 + Dijkstra 最短路；命题明确不拿路网数据，只能黑盒调用路径规划 API；
- **应对策略**：
  1. **扇形采样 + 二分探测**：N 方向 × 每方向 4~6 次路径规划调用定位临界点（单圈约 100~200 次调用，需配合配额估算）；
  2. **批量矩阵替代**：一次"中心点 → 多采样点"批量调用，把 N 次请求压成 N/50 次；
  3. **空间插值**：IDW/样条对采样点构建时间场，提取 15 min 等值线；
  4. **连通性修补**：对凹陷/飞地，用"测时结果 + 已知不可达点"做连通区域推导（评分细则原文鼓励项，需在文档中重点论证合理性）。

### 难点 2：精度与 API 成本的平衡

- 采样越密圈越准，但配额线性燃烧。策略：粗采样（16 方向）→ 梯度大的方向加密（至 64）；对时间场做局部线性假设控制误差；文档中给出**误差-成本曲线**（评审加分）。

### 难点 3：限流下的吞吐优化（30% 权重核心）

- 令牌桶对齐百度 QPS 限制；批量矩阵 + 合理并发（Promise 池）；两级缓存（坐标级 POI 缓存、OD 对测时缓存）；演示模式走缓存快照。

### 难点 4：盲区识别口径的严谨性

- "周边 1 公里"存在**直线 1 km vs 路网 1 km** 两种口径，建议：默认按命题字面直线 1 km（易复核），报告同时给出路网口径结果，并在文档中显式声明口径——评审视角这是严谨性加分项。

### 难点 5：等时圈几何正确性

- 凹包/样条拟合易自交；需要多边形有效性校验（自交检测、简单多边形修复）；飞地需 MultiPolygon。

### 难点 6：可复现演示

- 评审要求"Docker 或环境配置文件保证快速跑通"：docker-compose 一键启动 + `.env.example` + 固化示例社区数据 + 离线兜底模式，三者缺一不可。

## 7. 评分维度 → 技术对策映射

| 评分维度 | 权重 | 技术对策（本报告对应章节） |
|---------|------|--------------------------|
| 功能正确性与覆盖率 | **40%** | API 稳定调用（M1 §3）；等时圈热力图渲染（M2/M5 §3）；1km 盲区识别硬指标（M4 §3、难点 4） |
| API 深度调用与工程优化 | **30%** | 批量距离矩阵 + 并发（M1、难点 3）；容错降级（§5.1）；扇形采样/空间插值创新（难点 1——**命题明确鼓励**） |
| 产品交互与用户体验 | **15%** | 热力图/柱状图/雷达图三件套（M5）；自定义中心点双入口；异步进度反馈 |
| 开源工程规范 | **15%** | 模块化架构（§3 六模块）；README + Key 脱敏 + 部署指南；GitHub Actions/Gitee Go CI（M6） |

> 结论：**40% 功能正确性是及格线，30% 工程优化（尤其"创新空间插值"）是拉开名次的决胜区**，资源投入建议按 4:3 分配，UI 与工程规范用成熟方案快速达标。
